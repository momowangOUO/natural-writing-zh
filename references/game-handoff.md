# 游戏文本先写后接入

此流程适用于新增或改写台词及玩家可见文案。只修逻辑或原样搬运已有文本，不要求重写全文。只要求文案时停在文本交付；用户已要求实现时自动继续接入。

## 1. 读取约束

先读取项目相关说明、文本资源及上下文，确认角色、场景、分支、触发、显示时机、长度、变量、标签和目标位置。沿用现有 JSON、脚本、资源表或本地化方式，不自行替换存储体系。

## 2. 独立成稿

在项目现有文案目录保存纯文本稿；没有约定时使用工作目录下的 game-text 子目录。不要先在代码字符串中现场编台词，再反向导出冒充初稿。

按场景或界面流程连续组织。编号、角色、触发条件、分支和目标位置与正文分开。初稿可自由排版；需要附带校验工具时，使用下面的编号文本块，正文保持可直接阅读，不做 JSON 转义：

    ## repair.ready
    角色：林岑
    条件：接线完成，等待通电
    目标：沿用项目中对应节点

    ~~~~text
    接好了，试一下。
    ~~~~

每个编号对应一条目标文字。多行正文保留实际换行。带四个波浪号的行是正文边界，不属于游戏文字；若正文自身确实包含该边界，改用项目已有文本格式并采用相应校验方式。

## 3. 顺读与检查

读取当前任务需要的台词或界面参考。整场景、整分支或整段操作顺读，检查人物知识、指代、回应、触发和关键操作信息。确认后保存接入版文本。自检是内部步骤，不增加每批都需用户审批的要求；用户明确要求审稿时遵从。

## 4. 接入

实现 agent 以接入版正文为依据，只处理目标映射、转义和项目所需格式。移交给另一个 agent 时，提供文本稿及确切的节点、角色、条件与变量约束；同一个 agent 也按先写文本、后改目标的顺序完成。

不要在接入时顺手“润色”。如长度、术语或新发现的上下文需要改文案，先更新纯文本稿并复查，再同步目标。保留已有 ID、逻辑分支与无关文本。

## 5. 读回验证

从真实目标文件或运行时导出本批变更的“编号→已解码文本”，与纯文本稿逐条比较。检查编号、完整正文、空白、换行、变量和标签，不把格式转义误判为文字差异。

可使用 scripts/verify_game_text.py：传入 --source 文本稿路径和 --actual 已解码 JSON 导出路径。JSON 仅是核对用中间格式，不要求项目改用此格式。导出应只含本批编号，不能用初稿本身充当目标读回结果。

该工具只验证文字一致，不验证语言质量、角色绑定、分支、变量赋值或屏幕呈现。另行检查目标节点的角色与跳转、相关路径以及真实显示。没有可运行项目时，明确记录无法完成的验证，不声称已通过。
